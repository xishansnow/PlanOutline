# 交接（handoff）

目标：让另一台电脑上的新会话只读 `CLAUDE.md` 与 `工作进展.md` 就能接着工作。

本次参数：`$ARGUMENTS`

- 参数为空或为 `save`：执行下文“保存模式”。
- 参数为 `resume`：执行下文“恢复模式”。
- 其他参数：告诉用户可用的是 `/handoff`、`/handoff save` 与 `/handoff resume`，不执行任何操作。

## 保存模式（结束工作时）

1. 了解现状
   - 运行 `git status` 与 `git log --oneline -10`，确认本次会话改动了哪些文件、有哪些尚未提交。
   - 读取当前的 `工作进展.md` 与 `CLAUDE.md`。

2. 更新 `工作进展.md`（保持原有五节结构：已完成、决策记录、核对依据、待核对、待办；不要整篇重写）
   - 把“最近更新”改为今天的日期。
   - 已完成：追加本次会话完成的工作，每项一句，写清改了哪个文件、哪一节。
   - 决策记录：追加本次做出的结构性或立论性决定，每条写明决定了什么、理由、否决或保留作对照的方案；若本次推翻了旧决定，修改原条目并注明原因，不要留下互相矛盾的两条。
   - 核对依据：本次在线核实的内容，记下来源（链接或 DOI）与一句结论，尤其是原文摘句、不同来源之间的出入与年份口径。
   - 待核对：加入本次产生的、尚未在线核实或由推断得出的内容；已经核实的条目移入“核对依据”。
   - 待办：加入新的后续工作；已完成的条目移入“已完成”。
   - 只写事实，不写会话过程；数字、编号与文件名要与仓库内容一致。

3. 更新 `CLAUDE.md`（仅在需要时）
   - 只有当本次会话形成了新的、长期适用的约定（写作规范、文献要求、目录结构、编辑注意事项）时才修改。
   - 一次性的进展或待办不写入 `CLAUDE.md`。

4. 提交
   - 把本次会话改动的文档与 `工作进展.md` 一并 `git add`，提交说明用英文概括本次改动。
   - 不要提交与本项目无关的文件；不确定时先询问用户。

5. 推送前确认
   - 显示 `git status -sb`，告诉用户本地领先远程几个提交。
   - 询问用户是否推送；得到明确同意后再执行 `git push`。

6. 汇报
   - 用几行告诉用户：工作进展更新了哪些内容、提交号、是否已推送，以及在另一台电脑上继续的方法（`git pull` 后打开本目录，运行 `/handoff resume`）。

## 恢复模式（开始工作时）

1. 同步仓库
   - 运行 `git status -sb`。若有未提交的本地改动，先告诉用户并询问如何处理，不要擅自覆盖或丢弃。
   - 工作区干净时运行 `git pull --ff-only`。若无法快进（本地与远程分叉），停下来说明情况并询问用户，不要自行合并或变基。
   - 运行 `git log --oneline -5`，记下最新提交。

2. 读取交接内容
   - 读取 `工作进展.md`（`CLAUDE.md` 已自动加载，无需重复读取），尤其是“决策记录”，后续修改不得与其中的决定相抵触，除非用户明确要求推翻。
   - 若“已完成”或“待办”中提到具体文件，只在需要核对时再打开，不要一次读完所有文档。

3. 检查一致性
   - 核对 `工作进展.md` 中提到的文件是否存在；若“最近更新”日期早于最新提交日期，或最新提交的改动未反映在进展中，向用户指出，提示上次可能没有运行 `/handoff`。

4. 汇报并请用户选择
   - 用简短的几行说明：当前最新提交、上次更新日期、已完成的要点。
   - 列出“待核对”与“待办”中的事项并编号，请用户选择从哪一项开始；用户选定之前不要开始修改文件。
